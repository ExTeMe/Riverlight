# Git 与 GitHub 工作流程

更新：2026-11-08。当前为单人开发。日常顺序：明确目标 → 实现 → 必要检查 → 提交并集成 dev。

## 工作入口

- 读取 AGENTS、关联 Issue 与本次改动涉及的规范，检查 Git 状态和最近提交，保护已有改动。无需每次通读全部文档。
- Issues 保留任务目标、实际技术依赖和验收条件；用户当前指示优先于历史流程约束。明确的小修可直接开展，记录随交付补充。
- 无需认领、执行者代号、资源锁、机器人回执、交接释放、过期提醒或多人审批。历史认领不阻塞工作。
- Project 仅辅助查看任务；关联异常、元数据分诊或同步失败不阻塞实现与集成。真正缺少的接口、资产或需求仍需解决。
- 城市功能按需读 PROJECT_BRIEF、SYSTEMS、IMPLEMENTATION；资产另读 ASSETS；阶段目标与固定场景见 DEVELOPMENT_PLAN。流程改动无需读取无关产品章节。

## 分支与提交

- 从 dev 创建任务分支，同一任务续用原分支。优先复用当前合适工作区，不为单人工作额外创建 worktree。
- 按完整修复或功能步骤提交，只包含本次负责的改动。提交前审阅 diff，保护凭据、本机信息和用户存档。
- 任务分支经 PR 集成 dev，说明问题、最终改动、验证和限制，使用“关联 #编号”。检查当前 diff 即为日常自查，不另找审查者、不登记审查 SHA、不生成审查回执。
- 当前版本的 check 通过且实际问题已解决即可合并 dev；无需 collaboration、maintainer-review、认领或看板门槛。提交、推送、dev 集成和已有开发预览更新已授权。
- main 合并与正式发布仍需用户明确授权。main/dev 禁止强推和删除；源码不提交 dist。
- 合并后核对 CI/预览结果；失败则修复。工作结束报告提交与未提交内容。

## 按改动执行检查

| 改动 | 必要检查 |
| --- | --- |
| 文档、模板 | 审阅内容与相关链接；无需应用构建或浏览器 |
| 管理脚本、工作流 | 受影响的定向测试；无需城市浏览器回归 |
| 城市功能、依赖、站点 | 相关测试与构建；在实际浏览器检查受影响功能、画面和动态 |
| 模型、资产 | 源文件与导出完整性、元数据和浏览器实际表现 |
| 存档、占地、水系或共享接口 | 对应兼容、迁移和失败恢复检查；操作用户原城前备份 |

CI 保留 check：隐私与文档链接检查，以及按变更范围执行的构建/产物检查。本地按影响运行测试；已通过的相同版本与环境结果直接复用，不要求本地和 CI 重复全套。新增文件须纳入隐私检查。修复本次引入的错误，说明未验证范围，不宣称未经测量的性能。

## 验收与记录

Issue/PR 记录最终结果、提交版本、必要复现步骤及验证摘要即可；日志保留在 Actions 或聊天。不再生成验收准备、范围摘要、版本确认回执或单独的客观验收审批。

编写 PR 或 Issue 时，按需附上能更清楚展示改动、复现问题或支持验收的截图或 GIF。数量以讲清场景和行为为准。用足够的原始分辨率采集，发布前确认关键文字、边界与动作看得清。用 GitHub 原生附件上传，例如 GitHub CLI 的 `--attach`。证据文件留在临时输出目录，禁止随源码提交。上传前检查画面中的本机信息、凭据和私人数据。

客观任务按实际检查结果完成；主观画风、模型和氛围仍由用户确认，可直接在聊天确认并据实记录，不要求用户到 GitHub 填表或关闭任务。待画面确认不阻塞其他可独立开发的工作。不得伪造确认、测试或关闭尚未完成的任务。

行为或接口变化更新对应 IMPLEMENTATION/SYSTEMS；资产使用方式变化更新 ASSETS/README。内部调整不机械更新全部文档。任务未完成时留下简短下一步。

## 自动化维护

旧多人管理工作流退役：停止认领、审查登记、验收准备、定时全量看板同步。已有 Issues、Project 和历史证据保留；不清空用户数据。仓库设置脚本的 dev 目标仅要求 PR 与 check，无需 collaboration。

本地配置变化不等于线上已经启用。远端规则或默认分支仍使用旧入口时，须明确报告并核实迁移结果；main 的修改仍遵守明确授权边界。

## 分支收尾

最终批次集成后，在确认无未推送提交、开放 PR、其他工作区占用后清理任务分支；本地使用普通删除，不强制丢弃内容。未完成任务保留分支。

## 提交前的本机信息保护

不提交凭据、真实本机绝对路径、机器专属配置、缓存、日志或私人存档。保留 Blender 源与 GLB。隐私扫描及 diff 审阅用于交付检查，不日常重写历史。
