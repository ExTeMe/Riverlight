# Git 提交约定与本机信息保护

更新：2026-10-10。每次开始、继续中断任务或恢复上下文时必须阅读本文件与根目录 AGENTS.md。

## 已确认：所有后续修改均用 Git 记录

项目已初始化 Git 并连接 `https://github.com/ExTeMe/Riverlight.git`；初始历史已完成本机路径清理。每次工作重新检查实际分支、工作区及暂存区，不以历史记录推断当前状态。

- 日常代码开发、模型制作、配置与文档更新统一在 `dev` 分支提交，不为普通文档更新另建分支。开始时先确认位于 dev；切换前保护所有未提交改动。main 的更新遵循用户明确授权。
- 每次修改前检查分支、远端、工作区、暂存区与最近提交，识别用户已有改动；只提交本轮负责的文件/片段。
- 所有后续代码、模型、配置、测试及文档修改都应在合理边界提交。一个可解释的小功能、独立缺陷修复、资产批次或文档决策形成一个 commit；不每次保存都提交，也不等整个项目全部重做完才提交。
- 一个任务可有多个 commit。例如先提交数据契约和对应验证，再提交编辑界面，再提交联调修复；每项独立改动完成相关检查后及时落点。
- commit 前检查 diff、暂存范围、相关验证和文档同步。提交消息说明具体目的，建议 `类型(模块): 描述`，可包含 BACKLOG 任务 ID。
- 中断或交接前保存所有本轮改动；未完成但需要保存时提交明确标为 `wip` 的工作记录，写明缺口，不能当作阶段验收完成。未完成工作避免进入已配置自动发布的分支。
- 不以无意义的空提交或过度拆分代替记录；不得为了整洁而丢弃用户改动、擅自重写历史或强推。
- `.blend` 源与 GLB 导出、必要元数据一起维护；`node_modules/`、构建产物 `dist/` 和临时缓存不纳入源码提交。
- commit 与 push/发布分别处理。用户授权本地阶段提交，并随后明确要求清理路径及既有历史；这允许为本次安全整改重写历史并替换远端 main。历史整改不扩展为日常 push/发布授权。
- 提交前运行 `npm run check:privacy`，并人工检查 diff、凭据和二进制资源；不提交真实本机路径。环境变量在开发者本地设置，实际值不写进公开文档。扫描支持文本与可读个人目录元数据，不能解压所有二进制格式或代替凭据扫描。
- 每次结束检查 Git 状态，在交接中报告本轮提交及未提交内容；PROGRESS 记录任务、验证和后续步骤。无需为了把提交自身的 hash 写进同一提交而循环追加文档提交。

## 记录范围

尚未确认的讨论只保留在聊天中，不写入仓库文档或 commit 消息。文档与提交只记录已确认的规则、需求、实际改动及验证结果。

## 本次历史清理的结果与边界

已将唯一初始提交重写为安全整改版本，保留项目内容；使用预期远端提交校验更新 main，随后核验 GitHub 只有清理后的 main。已清理本地含旧路径的工具快照、reflog 和无引用对象，旧初始提交不再存在于本地对象库。检查结果记录于 [PROGRESS.md](PROGRESS.md)，日常阶段提交继续使用正常提交，不改写已发布历史。

这不能保证 GitHub 旧 SHA 缓存、他人的克隆/fork 或 PR 引用消失；旧副本不得重新推回仓库。必要时由所有者依据 [GitHub 历史清理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) 联系 Support，平台是否处理取决于其敏感数据政策。
