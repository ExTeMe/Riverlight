# Git 与 GitHub 工作流程

更新：2026-10-13。每次开始或恢复工作先读本文件，再查看 GitHub 当前任务。

## 工作入口

- 任务、阶段、负责人、优先级、依赖与验收证据在仓库 Issues/Projects 管理；本地文档只维护产品需求、系统接口、阶段出口及实现边界。
- 从已明确范围和验收、前置条件已满足的 Issue 开始。同一时间保留一个主要交付目标。
- 新事项先查重和分诊；P0 存档损坏、启动失败、核心建造失效优先调整当前工作，其余排入计划。
- 实现结束补充提交/PR、版本、复现和验证证据，进入待验收。代理负责客观检查，画风、模型和氛围由用户确认。验收通过才关闭 Issue；阶段出口通过后才关闭阶段父任务。

## 自动化维护

管理工作流使用 GitHub API，不依赖 CLI。初始化阶段里程碑、父子任务和依赖，关联个人 Project；任务事件同步最新状态。以 Issue 的互斥状态标签为操作入口，Project 显示自动同步的状态：

| Issue 操作 | Project 状态 |
| --- | --- |
| 开放，无状态标签 | 待办 |
| status:in-progress | 进行中 |
| status:review | 待验收 |
| status:blocked | 阻塞 |
| 验收通过后关闭 | 完成 |

切换时移除旧状态标签，不同时手动修改 Project 状态。视觉任务只有在收到用户对当前版本的确认后才加 visual-approved；否则提前关闭仍显示待验收。自动化不关闭任务、不合并 PR，也不把部署当作验收。

管理同步每次核对所有任务，并每六小时补做全量核对；不是依赖每个事件都成功送达。`management:triage` 标记元数据、未知依赖、循环或状态冲突；`management:ready` 表示任务及所属阶段的前置已验收，执行前仍须确认下面的开始条件。优先级标签由正文的唯一优先级生成，旧标签会移除。

Project 提供“当前可开始”“当前工作”“等待验收”“阻塞与分诊”视图；状态与就绪信息仍以 Issue 为操作入口，不另设本地清单。四个同名视图由初始化维护，其他自定义视图保留。

项目入口从仓库 Projects 页访问，不维护本地任务链接清单。自动化缺授权或失败时，明确报告未同步；必要离线交接暂存 PROGRESS，恢复后归入 Issue。具体行为和权限见 [管理工作流规范](../spec/spec-process-cicd-project-management.md)。

## 需求、问题与验收契约

### 可以开始的任务

- 有稳定任务编号、阶段、唯一优先级、明确前置（没有则填“无”）和视觉验收类型。新表单尚未分诊时保留“待分诊”，不能当作无依赖。
- 说明使用场景、用户可见目标、包含/不包含的范围、原型差距和规范引用。系统章节 S01～S13、场景 T01～T07 使用稳定编号；Issue 的验收项使用“任务 ID/AC01”等编号，修改文字不重新编号。
- 每个验收项包含初始条件、逐步操作、预期结果、判定方法；相关任务覆盖无效输入、边界、取消/失败恢复、撤销重做、拆改和旧档迁移。
- 视觉任务有固定近中远镜头与参照；动态任务有可重复过程；性能任务先确定实测方法。未知预算、误差或美术标准注明待测/待确认及前置任务，不能伪造承诺。
- 描述深度随任务接近执行而增加：远期保留目标与边界，近期补齐可执行细节；没有解决关键问题时不进入实现。

### 问题与证据

缺陷记录版本、最小场景、操作、预期/实际、出现频率、影响、证据、恢复方法、原任务与回归条件。区分“用户报告”“已复现”“能力缺失”“待复现”；未复现不等于问题不存在。

验收证据在 Issue 的“验收记录”中维护：完整提交 SHA、场景 ID/版本、初始化与镜头/环境、操作与实际结果、截图/动态证据、Actions 链接、限制。逐次测试日志留在 Actions 与聊天，PR 只说明问题与最终改动；不把这些日志复制进规范。用户原城先备份，附件脱敏，不上传本机路径或私人存档。

### 视觉确认与完成

视觉 Issue 的“验收记录”使用以下字段：`交付版本`、`验收版本`（完整且相同的提交 SHA）、`验收范围摘要`、`验收证据`（GitHub 链接）、`确认来源`（记录用户确认的 Issue 评论链接）。只有收到用户对该版本的确认才添加 `visual-approved`。评论不得由代理自行批准画面，可由代理据用户明确确认记录其范围与版本。

范围摘要由 `scripts/github-management.mjs` 的 `acceptanceFingerprint` 计算：标题与“验收记录”之前的需求正文参与摘要；“验收记录”“执行记录”“交接记录”不参与。交付版本变化或需求范围变化会使旧确认失效，重开移除确认标签。改变与该任务有关的实现时必须更新交付版本；自动化不能从所有代码提交猜测每项资产是否受影响。

非视觉任务仍由维护者根据客观证据验收后关闭。阶段父任务必须有已勾选的出口清单且本阶段子任务都完成，否则关闭后 Project 仍显示待验收；自动化不替维护者关闭阶段或里程碑。状态显示不代替复核原生 Issue 的关闭状态。

## 分支与阶段提交

- 日常代码、模型、配置与文档统一在 dev；不为普通文档更新另建分支。开始前检查分支、工作区、暂存区和最近提交，保护已有改动。
- 独立修复、功能步骤、资产批次或文档规则完成相关检查后及时 commit，不每次保存都提交，不积压到整个项目重做结束。提交引用任务 ID；只暂存本轮负责的内容。
- 独立完成并验收的一批改动创建 dev → main PR，关联 Issue 与证据，由用户确认后合并。不要每次 commit 同步 main，也不等整个阶段结束。
- main 保留审核后的源码，dev 网站为开发预览，gh-pages 仅存静态产物；dist 不进入源码分支。
- main 的目标保护为仅通过 PR 更新、源码检查 `check` 通过、讨论解决、禁止删除与强推；个人维护流程不要求另一位审核者。规则是否实际生效必须回读核验，私有仓库套餐或授权不足时明确报告。
- commit 与 push/发布分别处理；未完成工作不进入自动发布范围。
- 结束前核对 Git 状态并报告本轮提交与未提交内容。未完成任务保持开放，记录可恢复的下一步。

## 提交前的本机信息保护

- 仓库不得包含真实本机绝对路径、用户目录、凭据或机器专属设置。脚本从项目上下文或本地变量解析位置；文档使用仓库相对路径。
- 执行 npm run check:privacy，人工检查暂存 diff、凭据及二进制元数据；扫描失败先修复。新文件暂存后再扫描，确保纳入检查。
- node_modules、dist、缓存、日志及本地环境文件不提交；Blender 源与 GLB、必要元数据一起维护。
- 历史本机路径已按授权清理，不日常重写或强推；外部旧克隆/缓存可能仍存在，不能重新推回旧历史。
- 不把聊天流水或未确认讨论写入文档与 commit。只维护必要规则和可验证结果。
