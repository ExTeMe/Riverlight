# Git 与 GitHub 工作流程

更新：2026-10-15。本文件是开发操作、记录边界、认领、审查、验收和分支收尾的唯一流程依据。

## 工作入口

首次进入项目依次阅读本文件、PROJECT_BRIEF、GitHub Issues/Projects、DEVELOPMENT_PLAN、SYSTEMS、关联 Issue 及 IMPLEMENTATION；模型任务补读 ASSETS。续作或恢复上下文时重读本文件与关联 Issue，检查 Git 状态、认领、依赖和关联 PR，补读相关规范章节及上次阅读后的变更；无法判断变更范围时重新读相关文件。聊天摘要用于定位，不代替文件和验证。

- 任务、阶段、负责人、优先级、依赖与验收证据在仓库 Issues/Projects 管理；本地文档只维护产品需求、系统接口、阶段出口及实现边界。
- 从已明确范围和验收的 Issue 开始，核对依赖和有效认领。小团队按具体依赖、共享资源和审查能力协调并行范围，不设全局或每人固定数量限制；提前启动须由维护者明确范围与原因。
- 新事项先查重和分诊；P0 存档损坏、启动失败、核心建造失效优先调整当前工作，其余排入计划。
- 实现结束补充提交/PR、版本、复现和验证证据，进入待验收。代理负责客观检查，画风、模型和氛围由用户确认。验收通过才关闭 Issue；阶段出口通过后才关闭阶段父任务。

## 自动化维护

管理工作流使用 GitHub API，不依赖 CLI。初始化阶段里程碑、父子任务和依赖，关联个人 Project；任务事件同步最新状态。以 Issue 的互斥状态标签为操作入口，Project 显示自动同步的状态：

| Issue 操作 | Project 状态 |
| --- | --- |
| 开放，无状态标签 | 待办 |
| status:in-progress | 进行中 |
| status:code-review | 进行中；代码审查字段区分草稿、待审查、需修改和已审查 |
| status:review | 待验收 |
| status:blocked | 阻塞 |
| 验收通过后关闭 | 完成 |

切换时移除旧状态标签，Project 由自动化同步。验收者检查待验收任务后直接选择 **Close as completed**；工作流记录该次关闭对应的版本和范围，自动更新验收标签与 Project，无需评论或手动改看板。缺交付记录、非授权者关闭、PR 自动关闭以及 Close as not planned 不算验收。自动化不代替验收者关闭任务或合并 PR。

相关事件及每六小时补偿运行全量核对；普通讨论评论不启动同步。一次运行复用评论、阶段关系及权限读取，不建立持久本地状态表。代码审查确认和验收准备单独处理，看板字段随后续同步更新。`management:triage` 表示元数据或依赖冲突；`management:ready` 只表示已知前置通过，仍须核对开始条件。优先级由正文唯一值生成。

Project 提供“当前可开始”“当前工作”“等待验收”“阻塞与分诊”“我的任务”“代码审查”“认领需协调”视图；状态与就绪信息仍以 Issue 为操作入口，不另设本地清单。初始化维护同名视图，保留其他自定义视图。负责人使用原生 Assignees；执行者、任务分支、交付范围、独占资源、认领更新时间、代码审查、产品验收与发布状态由自动化投影。

## 认领、隔离和交接

GitHub 用户是主负责人，执行者代号区分真人和共用账号下的 AI 聊天。执行者代号不能包含本机路径或本地聊天链接。每个可独立验收任务只保留一名主负责人；多人协作先明确子任务或辅助范围，不能让两份实现都声称拥有同一交付。

开始前在任务 Issue 填写认领。可用 `npm run workflow -- claim --scope "道路中心线与拓扑契约" --add-files "src/roads.js"` 生成评论，自动读取当前分支及生成执行者代号，也可显式指定执行者。工具只生成文本，由已连接工具提交，不申请新凭据。手写示例：

```markdown
## 任务认领

- **执行者**：道路开发代理 A
- **执行者代号**：agent-road-a
- **任务分支**：23-road-contract
- **交付范围**：道路中心线与拓扑契约
- **独占文件**：src/roads.js
- **独占会话**：无
```

自动化按仓库串行处理并回读现状，只有收到 `github-actions[bot]` 的成功回执才能开始。负责人按评论实际作者记录，不由正文冒名指定。任务、分支和声明的独占资源冲突时拒绝第二次认领。独占文件填写仓库相对路径，多项以顿号分隔，目录覆盖其子文件；同一 Blender 会话填写 `shared-session`，共享库或同一二进制文件也需独占。回执以中文字段展示，机器状态隐藏在评论元数据中，不展示 JSON 正文。

维护者可加入“提前启动原因”，明确探索或基础设施工作的范围；不能借此绕过元数据分诊、占用他人资源或宣称阶段出口通过。未声明为独占的代码文件仍须通过接口协调与 PR 集成解决冲突。

中断保留认领。工作有进展时更新；简化工具读取已连接工具提供的最新评论快照：`npm run workflow -- update --snapshot <临时快照文件> --add-files "src/core.js"`，自动填认领编号和执行者。`--remove-files` 移除指定文件，未填写会话则保留，填写则替换整组会话。交接使用 `release --snapshot <临时快照文件> --scope "任务下一步"`。临时快照不提交、不作状态表；服务端仍核验实际作者、原认领编号与资源冲突，过时快照不能释放继任者。原有格式继续支持：

```markdown
## 认领更新

- **认领编号**：123456
- **执行者代号**：agent-road-a

## 任务交接

- **认领编号**：123456
- **执行者代号**：agent-road-a
- **交接说明**：已提交契约；下一步核对桥头高度消费者
```

更新与交接分别使用独立评论。“认领编号”是成功认领请求的评论 ID。手写资源字段替换整组资源，新增占用仍检查冲突。释放前保存可恢复工作和任务下一步；维护者代办写“代办原因”。接收者重新认领并等成功回执。待验收任务保留实现和证据，释放不等于完成。

长期无更新只加 `management:stale` 提醒协调，默认七天，可通过仓库变量调整；不自动清空负责人、释放资源或关闭任务。并行工作使用独立 checkout/worktree；Git 索引、分支切换、运行端口、缓存和存档都要隔离，禁止在同一目录相互切分支。

共享接口/存档格式变更先明确契约、影响任务、迁移方案与相关审查者。CODEOWNERS 用于路由审查，不能代替任务认领；共享账号不能提供独立身份的人工批准。协作者由项目所有者分别授予仓库和 Project 权限。

项目入口从仓库 Projects 页访问，不维护本地任务链接清单。自动化缺授权或失败时，在聊天中明确报告未同步；必要的任务级离线交接暂存 PROGRESS，恢复后只将任务下一步与技术阻塞归入 Issue。具体行为和权限见 [管理工作流规范](../spec/spec-process-cicd-project-management.md)。

## 需求、问题与验收契约

### 可以开始的任务

- 有稳定任务编号、阶段、唯一优先级、明确前置（没有则填“无”）和视觉验收类型。新表单尚未分诊时保留“待分诊”，不能当作无依赖。
- 说明使用场景、用户可见目标、包含/不包含的范围、原型差距和规范引用。系统章节 S01～S13、场景 T01～T07 使用稳定编号；Issue 的验收项使用“任务 ID/AC01”等编号，修改文字不重新编号。
- 每个验收项包含初始条件、逐步操作、预期结果、判定方法；相关任务覆盖无效输入、边界、取消/失败恢复、撤销重做、拆改和旧档迁移。
- 视觉任务有固定近中远镜头与参照；动态任务有可重复过程；性能任务先确定实测方法。未知预算、误差或美术标准注明待测/待确认及前置任务，不能伪造承诺。
- 描述深度随任务接近执行而增加：远期保留目标与边界，近期补齐可执行细节；没有解决关键问题时不进入实现。

### 问题与证据

缺陷记录版本、最小场景、操作、预期/实际、出现频率、影响、证据、恢复方法、原任务与回归条件。区分“用户报告”“已复现”“能力缺失”“待复现”；未复现不等于问题不存在。

验收证据在 Issue 的“验收记录”中维护：完整提交 SHA、场景 ID/版本、初始化与镜头/环境、操作与实际结果、截图/动态证据、Actions 链接、限制。逐次测试日志留在 Actions 与聊天，PR 只说明问题与最终改动；不把这些日志复制进规范。用户原城先备份，附件脱敏，不上传本机路径或私人存档。

### 记录边界

Issue 保留需求/问题、验收条件、实现与证据引用，以及恢复任务所需的下一步和产品/技术限制；认领、资源释放和任务级交接属于必要项目记录。聊天或 Actions 保留逐次测试输出、等待审阅/合并、本机授权或工具限制、自动化启用操作及代理执行流水。PR 只写具体问题和最终改动，接口变化补充契约与受影响任务。

### 自助验收与完成

交付者将任务设为 status:review，并在管理工作流填写 acceptance_issue、acceptance_evidence 生成验收准备；delivery_sha 可指定完整交付 SHA，否则读取已有交付版本，未记录时使用所选 ref 的提交。准备记录列出版本、需求范围摘要和证据，不表示通过。审查确认、初始化与验收准备分别运行；重复准备不清空同版本有效确认。

授权验收者检查交付后，在 Issue 直接选择 **Close as completed** 即表示本次验收通过，无需等代理、发表评论、修改标签或 Project。视觉任务须由用户检查画面后关闭；PR 合并只表示代码集成，原生 PR 显示 Merged，关联 Issue 仍等待验收。PR 正文使用“关联 #编号”，避免使用 Closes/Fixes 触发自动关闭。

工作流核对关闭者、completed 原因、关闭事件及关闭前的准备记录，将确认人、版本、范围、证据和来源自动归档。无准备记录或提前关闭时，Project 保留待验收；由交付者补齐记录，验收者重开后再次关闭。同步运行失败可重跑原关闭事件；周期核对可以恢复已保存回执的投影，不会从后补的交付信息推测历史验收。阶段父任务还须满足出口清单与子任务门槛。

已有评论确认继续兼容，可选择引用准备记录；视觉标题为“视觉验收”，客观标题为“客观验收”：

```markdown
## 视觉验收

- **验收结论**：通过
- **验收准备**：本任务的验收准备评论链接
```

证据补充实际结果与限制，普通讨论不作为验收。

代理不得自行批准画面或替用户验收真实任务；客观验收由维护者按证据确认。自动化核验授权登录名、仓库写权限、SHA、范围摘要、真实关闭事件或兼容评论及重开记录，普通讨论不算确认。默认授权者为仓库所有者，新增验收者由所有者维护 `VISUAL_REVIEWERS`。共用账号无法区分真人与代理，代记必须基于真实用户确认。

新摘要使用 scope-v2，保留目标、范围、验收标准、兼容约束与未知需求章节，排除明确的执行/交接/实现证据记录及管理元数据，忽略清单勾选状态。需求、交付版本或重开使旧确认失效；补证据或勾清单不要求重新确认。旧摘要按旧算法核验，不追溯重写历史批准。相关实现变化时交付者更新版本，自动化不能推断任意代码提交影响哪些任务。

新任务由确认生成 `acceptance-approved`，视觉任务同时生成 `visual-approved`；有效确认失效时自动移除。既有非视觉任务的历史关闭结果保留，不追溯伪造确认。阶段父任务必须有已勾选的出口清单且本阶段子任务都完成，否则关闭后 Project 仍显示待验收；自动化不替维护者关闭阶段或里程碑。状态显示不代替复核原生 Issue 的关闭状态。

## 分支与阶段提交

- 代码、模型、配置和文档从最新 dev 创建任务分支；同一任务续用原分支。分支名符合 Git 规则即可，不强制工具前缀或固定命名格式；可用 `23-road-contract` 等便于识别的名称，任务关系以认领记录和 PR 为准。main/dev/gh-pages 不作为任务分支。开始前检查分支、工作区、暂存区和最近提交，保护已有改动。
- 首批有实际改动且通过相关检查后创建目标 dev 的 Draft PR，正文写 `关联 #编号`；同一任务不创建竞争实现 PR。准备审查时转为正式 PR。
- 独立修复、功能步骤、资产批次或文档规则完成相关检查后及时 commit，不每次保存都提交，不积压到整个项目重做结束。提交引用任务 ID；只暂存本轮负责的内容。
- 任务 PR 合入 dev 前解决与最新 dev 的冲突，源码检查 `check` 及当前版本的 `collaboration` 检查通过，由指定维护者/审查者集成。代码审查、dev 集成、产品验收和发布分开记录，合并不自动关闭 Issue。
- 原生 GitHub Review 的批准须来自不同账号并对应当前提交；共用账号时，由 `CODE_REVIEWERS` 授权的维护者通过管理工作流确认已核对的 PR 版本（默认仓库所有者）。工作流核验实际发起者、有效认领与当前完整 head，结果和范围保留在 Actions 状态与运行记录，明确标记为共用账号自动审查。PR 正文和评论不填写审查通过说明；源码检查也不能代替实际审查。新提交使旧结果失效，有未解决的 Request changes 时不放行，普通写权限不自动获得代审查权。
  工作流仅记录、核验已完成的审查，不自动阅读代码或代替实际审查。VISUAL_REVIEWERS 虽沿用视觉名称，也配置客观验收者；CODE_REVIEWERS 配置代码审查记录者。
- 独立完成并验收的一批改动创建 dev → main PR，关联 Issue 与证据，由用户确认后合并。多人集成时列明本批包含的任务，不能只因某一个任务已验收就发布 dev 上所有其他改动。
- main 保留审核后的源码，dev 网站为开发预览，gh-pages 仅存静态产物；dist 不进入源码分支。
- dev 的目标保护为 PR、`check` 与 `collaboration` 检查通过、讨论解决、禁止删除与强推。main 保持 PR、`check`、讨论解决及禁止删除和强推，合并仍须用户授权；共享账号不配置无法满足的自我人工批准要求。规则是否实际生效须回读核验，不能把配置代码当作启用。
- 已授权任务分支提交、推送及检查与审查通过后的 dev 集成，包括既有开发预览更新；不再直接推送开发提交到 dev。未完成或检查失败的改动只保留在任务分支。
- 开发预览显示提交缩写，页面元数据保留完整 SHA；证据写完整版本和固定场景。Actions 保存真实浏览器存档回归报告，自动检查不能代替主观画面验收。
- 结束前核对 Git 状态并报告本轮提交与未提交内容。未完成任务保持开放，记录可恢复的下一步。

### 按改动执行检查

| 改动 | 必需检查 |
| --- | --- |
| 文档、Issue/PR 模板、CODEOWNERS | 隐私、仓库相对链接、人工核对覆盖范围/锚点/规则一致性 |
| 管理脚本、管理工作流和对应测试 | 上述检查与管理、协作、CI 工具测试 |
| 城市功能、资产、依赖、站点工作流或未知影响 | 上述检查、完整自动测试、生产构建、产物及浏览器回归；视觉/动态变化保存固定场景证据 |

CI 始终执行 check，在步骤层选择范围。新 PR 提交取消旧检查；部署和认领串行，不取消正在执行的写入。自动浏览器存档回归不替代画面验收；资产另审查二进制元数据。实际行为/接口变化更新对应 IMPLEMENTATION/SYSTEMS，资产管线/使用方式变化更新 ASSETS/README。

### 分支收尾

分支收尾规则：一个 Issue 可以有多个顺序交付批次。最终批次合入 dev、合并后检查通过且没有后续提交或开放 PR 使用该分支时，删除远端任务分支；不启用 GitHub 的“每次 PR 合并立即删除”。清理前回读 PR、最新 head 和集成版本，远端删除使用预期 head 的 `--force-with-lease`；预期不符时停止协调，不覆盖并发推送。

本地由各开发者/代理收尾时核对：工作区干净、无未推送提交、无其他 worktree 使用，切到 dev 后使用普通 `git branch -d`。不使用 `-D` 丢弃未集成内容；条件不满足时保留并说明。main/dev/gh-pages 长期保留。未完成或中断任务不清理；产品待验收可释放认领并清理已交付分支，保留 Issue、PR、提交与证据。后续返工从最新 dev 创建同一 Issue 的新分支。

## 提交前的本机信息保护

- 仓库不得包含真实本机绝对路径、用户目录、凭据或机器专属设置。脚本从项目上下文或本地变量解析位置；文档使用仓库相对路径。
- 执行 npm run check:privacy，人工检查暂存 diff、凭据及二进制元数据；扫描失败先修复。新文件暂存后再扫描，确保纳入检查。
